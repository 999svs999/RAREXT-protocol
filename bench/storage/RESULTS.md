- **Decoder** is the decoder artifact when it is part of the protocol's cost.

  digest, plus PSNR where the slice has a raster interpretation.

## 1 GiB throughput and memory

Measured by `npm run bench:throughput` on 2026-10-23T00:43:18.622Z with Node `v24.15.0`
on Intel(R) Core(TM) i5-8257U CPU @ 1.40GHz. Both rows use the shipped erasure code at 4+2
and the same 1024 MiB payload. Each row runs in its own process, so peak
RSS is attributable to that path. Scope: encode/decode compute only, not HTTP or JSON
framing.

| Path | Payload | Shards | Stored | Encode | Encode throughput | Decode | Decode throughput | Peak RSS | Exact |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| in-memory `encodeBytes` | 1024 MiB | 6 | 1536.0 MiB | 91.75 s | 11.2 MiB/s | 21.46 s | 47.7 MiB/s | 3234.1 MiB | yes |
| streaming `encodeFileToShards` | 1024 MiB | 6 | 1536.0 MiB | 121.35 s | 8.4 MiB/s | 44.93 s | 22.8 MiB/s | 394.5 MiB | yes |

- **In-memory** holds the payload, every data block, and every shard at once. It is the
  API used by the MCP put/get path, which caps input at `RAREXT_STORAGE_MAX_BYTES`
  (8 MiB by default).
- **Streaming** reads 8 MiB chunks, appends each shard block to a file, and decodes from only
  4 of 6 shard files. Peak RSS is a function of the chunk size, not
  the payload size.
- Peak RSS comes from `process.resourceUsage().maxRSS`; peak fell from
  3234.1 MiB to 394.5 MiB (8.2x lower) at this payload size.
- HTTP and JSON framing are excluded. The holder protocol still speaks whole-shard
  JSON, so a streamed shard is not yet placeable over HTTP; see `erasure-stream.ts`.

## HTTP holder path: whole shards vs raw streaming

Measured by `npm run bench:network` on 2026-10-23T01:15:08.087Z with Node `v24.15.0`
on Intel(R) Core(TM) i5-8257U CPU @ 1.40GHz, using 4+2 shards and real holder child
processes on loopback. Client peak is `process.resourceUsage().maxRSS`; holder peak is
sampled with `ps` every 200 ms and is the maximum per-holder RSS. Scope: holder HTTP
transport and local disk, not codec development; encode is excluded from the streaming
rows because it is reported separately in the 1 GiB codec section.

| Path | Payload | HTTP body | Upload | Download | Client peak RSS | Holder peak RSS | Exact |
| --- | ---: | --- | ---: | ---: | ---: | ---: | --- |
| whole-shard JSON | 64 MiB | base64 JSON | 2.96 s (21.6 MiB/s) | 3.18 s (20.1 MiB/s) | 671.1 MiB | 286.7 MiB | yes |
| raw streaming | 64 MiB | raw PUT/GET | 0.78 s (82.6 MiB/s) | 3.20 s (20.0 MiB/s) | 249.9 MiB | 248.0 MiB | yes |
| raw streaming | 1024 MiB | raw PUT/GET | 9.96 s (102.8 MiB/s) | 50.33 s (20.3 MiB/s) | 249.1 MiB | 78.5 MiB | yes |

- The whole-shard JSON row stops at 64 MiB because the holder rejects request
  bodies over 32 MiB. A 1024 MiB blob at 4+2 needs
  256 MiB per shard, and base64 JSON is about
  341 MiB. The old path cannot store a blob this large, so
  its row is measured at the largest payload that fits and the streaming row carries the
  1024 MiB number.
- Raw streaming keeps client and holder peaks roughly flat between 64 MiB and
  1024 MiB; the whole-shard row's client peak includes encoding the payload in
  memory. On this machine the 1024 MiB streaming run was bounded by the
  8 MiB chunk size, not the payload size.
- A streamed placement records `chunkBytes`, `chunks`, and `chunkDigests` beside the
  normal shard records, so retrieval verifies each chunk and the whole-payload digest.
  Repair of a streamed placement is not implemented (it still re-encodes a payload in
  memory); the net demo's sealed repair uses the small in-memory placement.
